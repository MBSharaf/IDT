What happens when 5,000 visitors open the IDT website at once

A first-visit load test of the IDT catalogue site, and what the results mean for hosting it on SmarterASP.NET behind a Namecheap domain.

Tested 1 Nov 2026Site version c07a9b79 test runs · 1.2 million requests
Verdict

The website itself is light and fast. Whether 5,000 visitors at once get through depends on the hosting plan and on putting Cloudflare in front of it.

On SmarterASP's cheapest plan, which allows 200 connections at a time, most of those 5,000 visitors would see an error page. On a plan with unlimited connections plus the free Cloudflare CDN, the same spike is routine. The changes needed cost a few dollars a month and about an hour of setup.

5,000 visitors in the same minute, by setup

Fails

SmarterASP .NET Basic ($2.95/mo)

Capped at 200 concurrent connections. Only about 200 visitors can be connected at any moment; the rest get 503 Service Unavailable. In our model of this plan, 1,000 visitors in 10 seconds already failed 80% of requests.

Slow, probably survives

Advance ($4.95) or Premium ($7.95), no CDN

No connection cap. The limit becomes the shared server's network and CPU: 5,000 home-page loads are about 2.4 GB, which needs roughly 1.9 Gbit/s to deliver in 10 seconds or 320 Mbit/s over a minute. Expect pages that take several seconds or more to load at the peak.

Handles it

Advance or above + Cloudflare (free)

Cloudflare serves the images, CSS and JavaScript from its own network. SmarterASP then sees a small fraction of the traffic. SmarterASP lists this setup as "Cloudflare CDN Ready". This is the recommended setup.

How heavy the site is

Every page was opened in Chromium (1366 × 768, scrolled to the bottom) and every file it requested from the IDT host was recorded. A first-time visitor's journey is Home → Products → one product page → Contact.

Test results

Each virtual user made one full visit with a browser cache, waiting 3–6 seconds between pages. All users started within 10 seconds, which is the "everyone opens it at once" case. The test server behaves like IIS 10, the web server SmarterASP uses: gzip, ETag and Last-Modified, and no cache headers by default.

"Home page load" is all 48 home-page files fetched one after another. A real browser fetches several at once, so its page loads are faster. The Basic-plan failures were all 503 Service Unavailable, which is what IIS returns when a site reaches its connection limit.

Reading the results

  • Up to 1,000 simultaneous visitors, the site is flawless. There were no errors, a typical file arrived in under 5 ms, and a full home page took a quarter of a second.
  • Above 1,000, the test PC became the bottleneck. Every error in the gold-bar runs was "connection refused" on this one Windows PC. It was running 5,000 JMeter users and the web server at the same time, and its CPU hit 100%. A single machine cannot simulate 5,000 real visitors. That figure has to be measured on the real host with a cloud load generator (see the last step below).
  • The 200-connection cap is the clearest finding. It cannot absorb a spike: 300 visitors arriving within 10 seconds already lost a third of their home pages. The same plan handled 600 visitors spread over a minute without a single error. So Basic is fine for normal traffic and fails on a launch, a campaign or a viral post.
  • The real cap is lower than this test suggests. Browsers on HTTP/1.1 open up to 6 connections per visitor, and IIS keeps idle connections open for up to 2 minutes, so 200 connections can mean as few as about 33 visitors loading pages at once.

The reviews and contact form under a spike

The reviews and contact form go through a Google Apps Script web app. The home and product pages ask it for approved reviews once per visitor, and Google allows 30 simultaneous executions per account. This service was not load-tested, because it belongs to Google.

  • Reviews: with 5,000 visitors arriving together, most review requests will be refused at the peak. The pages still work; the reviews section just stays empty for those visitors.
  • Contact form: an inquiry sent during the peak may not reach the Google Sheet. The site already handles this: it tells the customer and offers to send the same inquiry by e-mail or WhatsApp, so the lead is not silently lost.

What to do before launch

  1. Choose ASP.NET Advance ($4.95/mo) or higher, not Basic.Basic's 200-connection limit is the one thing that turns a traffic spike into error pages. Advance and Premium list unlimited concurrent connections (SmarterASP plans page, 1 Nov 2026).
  2. Put Cloudflare's free plan in front of SmarterASP.At Namecheap, change the domain's nameservers to the two Cloudflare gives you. In Cloudflare, point the domain at SmarterASP's IP address, set SSL to "Full (strict)" (SmarterASP includes a free SSL certificate), and add a cache rule to cache everything. Cloudflare then serves almost all of the 0.52 MB per visitor from its own network.
  3. Upload web.config with the site.It is now in the repository root. It turns on gzip, lets browsers and Cloudflare reuse pages for 1 hour and photos for 7 days, and registers .webp and .json. Without that, IIS can return 404 for the product photos and the product data.
  4. Stop asking Google for reviews on every visit.Publish approved reviews as a small file on the site, refreshed when a review is approved, so the reviews section no longer depends on Google's 30-execution limit. The contact form can stay as it is.
  5. Test the real host before announcing the site.Ask SmarterASP support in writing first: an unannounced load test looks like an attack and can get the account suspended. Then run the same test plan from a cloud service that accepts JMeter files (for example BlazeMeter or Azure Load Testing), in steps of 100, 500, 1,000 and then 5,000 users, against the Cloudflare address.

Running the test again

The test plan and helper files are in perf/ in the repository. perf/README.md has the full instructions.

node perf/build-jmx.mjs                                  # rebuild the plan after pages change
node perf/static-server.mjs --port 8080                  # IIS-like local server
node perf/static-server.mjs --port 8082 --max-conn 200   # Basic-plan model

jmeter -n -t perf/idt-load-test.jmx -Jhost=127.0.0.1 -Jport=8080 \
  -Jusers=1000 -Jrampup=10 -l results.jtl -e -o report/

# against the live site (only with SmarterASP's written permission):
jmeter -n -t perf/idt-load-test.jmx -Jprotocol=https -Jport=443 \
  -Jhost=www.your-domain.com -Jusers=100 -Jrampup=60 -l live.jtl -e -o live-report/

Limits of this test

  • The site was not yet on SmarterASP, so it ran on a local server that copies IIS 10's default behaviour. Network distance, TLS and other customers on the shared server were not part of it.
  • The test generator and the server shared one PC (12 threads, 16 GB). Results above 1,000 simultaneous users measure that PC as much as the site.
  • SmarterASP does not publish CPU limits or network port speed for shared plans. The bandwidth figures above are calculations, not measurements.
  • Third-party services (Google Fonts, cdnjs, jsDelivr, Google Apps Script) were left out on purpose. Load testing them would put traffic on systems that IDT doesn't own.
  • JMeter fetches a page's files one at a time per user. Real browsers fetch about six at once, so the page-load times here are pessimistic, and the connection counts are optimistic.
